The latest release is **v1.1.3**, released November 19, 2026. To install or upgrade to it:

```bash
docker pull terrificci/zee3:1.1.3
curl -fsSL https://raw.githubusercontent.com/terrific-ci/z3/main/install.sh | sh -s -- --version 1.1.3
```

The `latest` image tag and the install script without `--version` always get this release; see
[Install](/deploy/install).

<Update label="v1.1.3" description="November 19, 2026" tags={["Latest"]}>

- **Imports:** a running import shows how far the current round is as a percentage of the source's size, the copy speed, objects checked per second and the time left; between rounds it shows how long the last round took, what it copied and when the next one starts. The first round counts the source in the background, later rounds use the previous round's size and count again when the source has grown. The counters now move with every object instead of every 1,000. See [Migrate from MinIO](/deploy/migrate-from-minio).
- **Console:** previews of images, PDFs and text show how much has arrived, the speed and the time left while they load. Files above 256 MiB still open directly in the browser.

</Update>

<Update label="v1.1.2" description="November 19, 2026">

- **Imports:** faster: the next listing pages are read while objects are still being copied, so one slow object no longer holds the rest back (2,000 small objects in 3.7 s instead of 4.7 s on a local link), and objects of 32 MiB and more are fetched as several ranges at once (about 29% faster one at a time over a 60 ms link). Over a link with latency, raising the job's objects in parallel helps small objects most. See [Benchmarks](/deploy/benchmarks).
- **Replication:** Replication → Peers and sites → This node's peer API shows a connection code with this node's name, address and peer token; pasting it into **Add peer** on another node fills in all three. The token field now says it is the other node's peer token and where to find it. See [Bucket replication](/replication/bucket-replication).
- **Fix:** copy buttons in the console did nothing when the console was opened over plain HTTP on another host than localhost.

</Update>

<Update label="v1.1.1" description="November 19, 2026">

- **Imports:** an import job's endpoint, access key, secret key, region and parallelism can now be changed in place: Import/Export → the job's menu → **Edit source and schedule**, or `zee3 admin import set <id> --region …`. The new settings are tried against the source before they are saved, and a failed job resumes with **Save and resume**, for example after `AuthorizationHeaderMalformed ... expecting 'id'`. See [Migrate from MinIO](/deploy/migrate-from-minio).
- **Health check:** `GET /api/health` also answers on the S3 port, so a load balancer in front of S3 can check the node without the console port.
- **Fix:** confirming a dialog in the console (Remove an import, Delete a bucket, and every other action that asks first) did nothing, because the confirmation was taken as Cancel. It now carries out the action.

</Update>

<Update label="v1.1.0" description="November 19, 2026">

- **Setup:** a new node started without `ZEE3_ACCESS_KEY` and `ZEE3_SECRET_KEY` opens a setup page in the console to choose the root account, instead of starting with built-in credentials. Nodes that already have data keep working as before. See [Install](/deploy/install).
- **Join a Zee3:** from the setup page, a new node finds the Zee3 nodes on its network (or takes a console address) and joins one's site group once root there approves a six-digit code, or right away with a one-time join code made under Replication → Peers and sites. The new node signs in with the same root account and buckets start replicating both ways. See [Site replication](/replication/site-replication).
- **Peer token in the console:** Replication → Peers and sites shows this node's peer API and lets root turn it on or change its token without a restart; a site group gets the new token automatically. `ZEE3_PEER_TOKEN` still takes precedence.
- **Policy editor:** policies, access key policies and bucket policies are edited visually in the console, with a raw JSON view.
- **Console:** date and time fields (logs range, access key expiry, retention, lifecycle, delete by condition, point-in-time rollback) now open a calendar picker instead of the browser's own control.

</Update>

<Update label="v1.0.0" description="November 19, 2026">

- **S3 API:** on port 9000: buckets, versioning, objects with ranges, metadata, tags and conditional requests and writes, `ListObjects` V1 and V2 with paging, `ListObjectVersions`, `CopyObject`, `DeleteObjects`, multipart uploads with `UploadPartCopy` and `partNumber` reads, `GetObjectAttributes`, additional checksums (CRC32, CRC32C, CRC64NVME, SHA1, SHA256) and presigned URLs, with results against MinIO Mint and ceph/s3-tests published. See [S3 compatibility](/api/s3-compatibility) and [S3 conformance](/api/s3-conformance).
- **MinIO compatibility:** the `/minio/health/*` endpoints, `/minio/v2/metrics/*` with an `mc admin prometheus generate` token, `x-minio-force-delete`, `metadata=true` on ListObjectsV2 and MinIO's quota and admin error codes.
- **Content-defined chunking:** with BLAKE3, identical data is stored once, every read verifies its hash, and `CopyObject` and completing a multipart upload copy no data.
- **Performance:** uploads hash and write several chunks at once while the body keeps arriving, downloads read and verify several chunks ahead of the client, and on Linux `ZEE3_IO_URING=1` reads chunks through io_uring. See [Benchmarks](/deploy/benchmarks).
- **Memory:** the metadata cache is capped (`ZEE3_META_CACHE_MB`, 128 MiB by default), so memory levels off instead of growing with the number of objects. See [Running alongside other services](/deploy/shared-host).
- **Erasure coding:** over a set of disks (`ZEE3_DISKS`), with healing that repairs damaged shards found by reads, refills a replaced disk, verifies everything on a schedule within `ZEE3_HEAL_DUTY`, and sweeps orphaned chunk files. See [Healing](/durability/healing).
- **Pools:** grow with a new disk set (`ZEE3_POOLS`), rebalance by capacity, and decommission a pool before removing it, with objects readable throughout.
- **Cluster mode:** several nodes act as one Zee3 through a Raft log, with each chunk kept on several members or as erasure-coded shards across them (`zee3 admin cluster ec 4+2`), members joining and leaving without downtime, and rolling upgrades. See [Cluster](/deploy/cluster).
- **Active-active replication:** between nodes and clusters over a pull-based peer API, with `async`, `quorum` and `all` consistency, prefix and tag rules, conflict resolution by hybrid logical clocks, Merkle anti-entropy and change-log pruning once every peer has applied a change. See [Replication](/replication/overview).
- **Site replication:** one call joins every site in a mesh, hub-and-spoke or chain topology, and keeps buckets, IAM, settings and other cluster documents in step.
- **Across sites:** read-your-writes with the `x-zee3-session` header, bandwidth limits and time windows per peer, data residency rules, and geo erasure coding with sites that rebuild lost shards from the others. See [Geo erasure coding](/replication/geo-erasure-coding).
- **Replication map:** the Replication page draws every node and link of the group, live, with lag, traffic, conflicts and errors per bucket in both directions. See [Replication map](/replication/map).
- **Edge and branch offices:** each peer shows whether it is online and how many changes wait, and with `on_offline: "local"` writes answer at once while the peers they need are offline. See [Edge and branch offices](/replication/edge).
- **Lean Replica:** a small node keeps only recent object data within a size or age window while metadata stays complete, reading older data through from a full replica. See [Lean Replica](/replication/lean-replica).
- **Mutual TLS between nodes:** `ZEE3_PEER_TLS_CERT`, `ZEE3_PEER_TLS_KEY` and `ZEE3_PEER_TLS_CA` secure replication, site replication and cluster traffic, with a step-by-step rollout for running groups. See [Mutual TLS between nodes](/deploy/peer-tls).
- **Lifecycle:** expiration, noncurrent versions, orphaned delete markers, aborting uploads, and transitions to tiers on AWS S3, MinIO or another Zee3, Google Cloud Storage and Azure Blob, with reads going through Zee3 transparently.
- **Object Lock:** governance and compliance retention, legal hold and default retention per bucket.
- **Deletion protection:** with a deletion delay on a bucket, permanently deleted versions go to a trash and can be restored until the delay has passed. See [Deletion protection](/storage/deletion-protection).
- **Rollback to a point in time:** a bucket, a prefix or one key goes back to how it was at a given time, previewed first and run as a batch job that only adds versions. See [Point-in-time rollback](/storage/point-in-time).
- **Bucket tags, quotas and compression:** quotas per bucket, and LZ4 per chunk for chosen names and content types.
- **Batch jobs:** replicate to another bucket or S3 store, expire with a dry run, and move encrypted objects to another KMS key without rewriting data.
- **IAM:** users, groups, AWS-style policies with conditions, access keys with their own policy and expiry, and bucket policies including anonymous access.
- **OpenID Connect, LDAP and STS:** sign-in for the console, and temporary S3 credentials from `AssumeRoleWithWebIdentity`, `AssumeRoleWithLDAPIdentity` and `AssumeRole`, narrowed by session policies and valid on every site. See [STS](/access/sts).
- **Encryption:** SSE-S3, SSE-KMS and SSE-C with a data key per object (AES-256-GCM per chunk), bucket default encryption, and an internal KMS or HashiCorp Vault, MinIO KES, AWS KMS, Azure Key Vault and Google Cloud KMS, with retired key stores still opening what they sealed. See [External KMS](/security/external-kms).
- **Bucket events:** to webhooks, Redis, NATS, Elasticsearch, Kafka, RabbitMQ, MQTT, PostgreSQL, MySQL and NSQ, with TLS, a queue that survives restarts and unreachable destinations, exactly one event per change across sites, and `ListenBucketNotification` for `mc event listen`. See [Bucket events](/events/bucket-events).
- **Audit, trace and logs:** every S3 request and admin change to webhook, Redis, NATS, Elasticsearch or Kafka in MinIO's format with secrets redacted, live trace, and server logs kept on disk, for one node or every node of a site group. See [Audit log](/audit/audit-log) and [Trace and logs](/audit/trace-and-logs).
- **Metrics:** running status, historical metrics per minute, hour and day for up to three years, per bucket too, and Prometheus metrics at `/metrics`.
- **Cluster settings:** changed at runtime: region, request limits, CORS, upload size, Signature V2, compression, scanner intervals and logging. See [Cluster settings](/operations/settings).
- **Support tools:** health checks, drive and network speed tests, CPU profiles with flame graphs, and inspecting how an object is stored.
- **File protocols:** WebDAV, FTP/FTPS, SFTP and NFSv3 over the same buckets and policies, off by default.
- **Import:** from MinIO or any S3 store, including bucket settings and deletions made during cutover, and configuration export and import between nodes. See [Migrate from MinIO](/deploy/migrate-from-minio).
- **Web console:** on port 9001 for everything above, with bucket search, file previews, bulk deletes, Find (⌘ K), dark and light themes and a phone layout. See [Web console](/operations/console).
- **Command line:** `zee3 admin` for settings, cluster, protocols, imports, batch jobs, support, pools, logs and metrics. See [Command line](/cli/overview).
- **Platforms:** Linux binaries for amd64 and arm64, a Docker image, and an install script. See [Install](/deploy/install).

</Update>
