The `z3` binary that runs the server also manages it. Without a command, `z3` runs a node.
`z3 admin ...` manages a **running** node through its [admin API](/api/overview).

Because the CLI goes through the API:

- it follows the **same rights** as the console: the identity you sign in with needs the admin
  rights the command needs;
- it **validates input the same way**, with the same error messages;
- every change it makes shows up in the [audit log](/audit/audit-log) under that identity.

Use it over SSH, on a server without a browser, in scripts and cron jobs.

## A quick example

On the server itself, where `Z3_ACCESS_KEY` and `Z3_SECRET_KEY` are already set for the node:

```bash
z3 admin support health
z3 admin settings set compression enabled=true
z3 admin protocols enable sftp
z3 admin metrics --range 7d
```

## Commands

| Command | What it does |
| --- | --- |
| [`z3 admin settings`](/cli/settings) | Show, set and reset cluster settings |
| [`z3 admin protocols`](/cli/protocols) | File protocols: state, turn one on or off |
| [`z3 admin batch`](/cli/batch) | Batch jobs: replicate, expire or rotate keys over many objects |
| [`z3 admin support`](/cli/support) | Health report, speed tests, CPU profiles, object inspection |
| [`z3 admin pools`](/cli/pools) | Pools: usage, rebalance, decommission |
| [`z3 admin metrics`](/cli/metrics) | Traffic and storage over a past range, node-wide or per bucket |
| [`z3 admin lean`](/replication/lean-replica#command-line) | Lean Replica: state, keep window, evict now, turn off |
| [`z3 admin gc`](#garbage-collection-and-the-orphan-sweep) | Run garbage collection now |
| [`z3 admin sweep`](#garbage-collection-and-the-orphan-sweep) | Delete chunk files a crash left unreferenced on this node |

Everything else (buckets, IAM, replication, events) is managed in the [console](/operations/console),
through the [admin API](/api/overview), or with any S3 client.

## Connecting and signing in

| Option | Environment | Default | What it is |
| --- | --- | --- | --- |
| `--url <URL>` | `Z3_ADMIN_URL` | `http://127.0.0.1:9001` | The node's admin API |
| `--access-key <KEY>` | `Z3_ACCESS_KEY` | `z3admin` | Who to sign in as |
| `--secret-key <SECRET>` | `Z3_SECRET_KEY` | `z3admin-secret` | Its secret |

The options belong to `admin`, so they go **between `admin` and the command**:

```bash
z3 admin --url https://z3-admin.example.com --access-key ops --secret-key "$OPS_SECRET" pools
```

Or set them once in the environment:

```bash
export Z3_ADMIN_URL=https://z3-admin.example.com
export Z3_ACCESS_KEY=ops
export Z3_SECRET_KEY=...
z3 admin pools
```

Each command signs in with `POST /api/auth/login`, runs, and is done; nothing is saved between
commands. Any identity the console accepts works: the root account, an IAM user (user name and
secret key), an access key and its secret, or an LDAP account when LDAP is set up. Using the same
variables as the server means that on the server itself, commands sign in as root without extra
options.

<Tip>
  For scripts, create a user or access key with only the rights the script needs, for example the
  built-in `diagnostics` policy for health checks and metrics. See
  [Users, groups and keys](/access/users-groups-keys).
</Tip>

## Getting help

`--help` works at every level:

```bash
z3 --help
z3 admin --help
z3 admin support --help
z3 admin support speedtest --help
```

```
Manage a running node (settings, file protocols) through its admin API

Usage: z3 admin [OPTIONS] <COMMAND>

Commands:
  settings   Cluster settings
  protocols  File protocols: state, or turn one on or off
  batch      Batch jobs: replicate, expire or rotate keys over many objects
  support    Health report, speed tests, CPU profiles, object inspection
  metrics    Traffic and storage over a past range, node-wide or per bucket
  pools      Pools: usage, rebalance, decommission
  help       Print this message or the help of the given subcommand(s)

Options:
      --url <URL>                Admin API of the node [env: Z3_ADMIN_URL=] [default: http://127.0.0.1:9001]
      --access-key <ACCESS_KEY>  [env: Z3_ACCESS_KEY=] [default: z3admin]
      --secret-key <SECRET_KEY>  [env: Z3_SECRET_KEY] [default: z3admin-secret]
  -h, --help                     Print help
```

`z3 --version` prints the version.

## Output and errors

Commands print plain text meant for people, one line per item. On success they exit with status
`0`. On an error they print `Error:` and the API's message, and exit with status `1`:

```bash
z3 admin settings set api requests_max=abc
# Error: api.requests_max is a whole number
```

| Message | Meaning |
| --- | --- |
| `cannot reach http://...` | Nothing answers at `--url`: wrong address, or the admin port only listens on `127.0.0.1` of another machine |
| `sign-in failed: Wrong access key or secret key, or the account is disabled` | Check `--access-key` and `--secret-key` |
| `this needs the admin:ConfigUpdate permission` | The identity lacks the right; see [Rights](/api/overview#rights) |

For machine-readable output, call the [admin API](/api/overview) directly; it answers JSON.
`z3 admin support health --json` prints the whole health report as JSON.

## Garbage collection and the orphan sweep

| Command | What it does | Right |
| --- | --- | --- |
| `z3 admin gc [--grace-secs N]` | Delete unreferenced chunks and abort abandoned multipart uploads now. `--grace-secs` replaces the configured grace period (`0`: collect now) | `admin:ConfigUpdate` |
| `z3 admin sweep [--dry-run] [--min-age-secs N]` | Walk this node's chunk directories and delete orphaned chunk files (written by uploads that crashed before their commit). `--dry-run` only counts; `--min-age-secs` replaces the minimum file age | `admin:ConfigUpdate` |

```bash
z3 admin gc
# 120 chunks deleted (402331221 bytes freed), 1 uploads aborted

z3 admin sweep --dry-run
# 2203128 chunk files checked in 4096 directories: 14 orphaned, 2 too recent to delete; would delete 12 (50331648 bytes) and 1 temp files (4194304 bytes) in 41200 ms
```

They call [`POST /api/gc`](/api/admin-operations#disks-healing-and-garbage-collection) and
[`POST /api/gc/sweep`](/api/admin-operations#orphan-sweep). The sweep's default minimum age is the
GC grace period (in cluster mode, at least `Z3_UPLOAD_TTL`); keep it on a node that serves traffic.
See [Orphaned chunks](/durability/healing#orphaned-chunks).

## Container health checks

`z3 healthcheck` asks the local node's `/api/health` (on `Z3_ADMIN_ADDR`) and exits with `0` when it
answers. It needs no credentials, which makes it a fit for a Docker `HEALTHCHECK`.
