z3 serves **plain HTTP** on all three ports. For anything beyond a private network, put a reverse
proxy in front that terminates TLS:

| Port | Typical public name | Notes |
| --- | --- | --- |
| 9000, S3 API | `s3.example.com` | Large request bodies, long transfers |
| 9001, console and admin API | `console.example.com` | Server-sent events for live trace, logs and events |
| 9002, replication API | `peer.example.com`, or a private network | Long-polling (requests held up to 20 seconds) |

Give the S3 API and the console **their own host names**. z3 uses path-style S3 addressing, so the
S3 API needs the whole host, and the console expects to be served from `/`.

Keep the z3 ports themselves off the public network: bind them to `127.0.0.1` (or publish them only
on `127.0.0.1` in Docker) when the proxy runs on the same machine.

## Caddy

Caddy gets and renews certificates by itself.

```caddyfile Caddyfile
s3.example.com {
	reverse_proxy 127.0.0.1:9000 {
		# Stream request and response bodies instead of buffering them.
		flush_interval -1
		transport http {
			read_timeout 10m
			write_timeout 10m
		}
	}
}

console.example.com {
	reverse_proxy 127.0.0.1:9001 {
		# Live trace, logs and event views are server-sent events.
		flush_interval -1
	}
}
```

Caddy keeps the original `Host` header, which S3 signatures depend on, and sets
`X-Forwarded-For` and `X-Forwarded-Proto` for z3. It has no request body limit by default.

## nginx

```nginx /etc/nginx/conf.d/z3.conf
server {
    listen 443 ssl;
    http2 on;
    server_name s3.example.com;
    ssl_certificate     /etc/ssl/s3.example.com/fullchain.pem;
    ssl_certificate_key /etc/ssl/s3.example.com/privkey.pem;

    # No size limit (z3 enforces its own) and no buffering of uploads or downloads.
    client_max_body_size 0;
    proxy_request_buffering off;
    proxy_buffering off;

    location / {
        proxy_pass http://127.0.0.1:9000;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        # S3 signatures cover the Host header: pass it through unchanged.
        proxy_set_header Host $http_host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 60s;
        proxy_send_timeout 600s;
        proxy_read_timeout 600s;
    }
}

server {
    listen 443 ssl;
    http2 on;
    server_name console.example.com;
    ssl_certificate     /etc/ssl/console.example.com/fullchain.pem;
    ssl_certificate_key /etc/ssl/console.example.com/privkey.pem;

    # Uploads from the console's bucket browser.
    client_max_body_size 0;
    proxy_request_buffering off;
    proxy_buffering off;

    location / {
        proxy_pass http://127.0.0.1:9001;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $http_host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        # Live views stay open.
        proxy_read_timeout 1h;
    }
}
```

On nginx older than 1.25.1, write `listen 443 ssl http2;` instead of `http2 on;`.

Keep `proxy_pass` without a path after the port, so nginx forwards the request path exactly as the
client signed it.

## Trust the proxy

Behind a proxy, every request comes from the proxy's address. To let z3 see the real client, add
the proxy to the cluster setting **`api.trusted_proxies`** (addresses or networks such as
`10.0.0.0/8`). For requests from a trusted proxy, z3 takes the client address from the first entry
of `X-Forwarded-For` and HTTPS from `X-Forwarded-Proto`. From anyone else, those headers are ignored.

This matters for [policy conditions](/access/conditions) such as `aws:SourceIp` and
`aws:SecureTransport`, on both the S3 API and the console.

<Tabs>
  <Tab title="Console">
    **Settings → API → Trusted proxies**: add `127.0.0.1` (or the proxy's address) and save.
  </Tab>
  <Tab title="CLI">
    ```bash
    z3 admin settings set api trusted_proxies=127.0.0.1,::1
    ```
  </Tab>
</Tabs>

<Warning>
  Because z3 uses the **first** address of `X-Forwarded-For`, the proxy must replace that header,
  not append to a value the client sent. The nginx example does this with
  `X-Forwarded-For $remote_addr`; Caddy ignores incoming `X-Forwarded-*` headers from clients it
  doesn't trust.
</Warning>

## Large uploads and timeouts

- **Body size.** z3 limits a single PUT or multipart part with the `api.max_object_size_mb` setting
  (5120 MiB by default). A proxy limit below that turns big uploads into `413` errors from the
  proxy; disable it (`client_max_body_size 0`) and let z3 decide.
- **Buffering.** Without `proxy_request_buffering off`, nginx writes each upload to a temporary file
  before z3 sees a byte. Turn buffering off in both directions.
- **Timeouts.** A slow client uploading a 5 GiB part needs minutes. Raise the proxy's read and send
  timeouts, or use multipart uploads with smaller parts (most clients do this automatically for big
  files).
- **Streams.** `ListenBucketNotification` on the S3 API and the console's live trace, logs and event
  views keep responses open. Turn off response buffering (`flush_interval -1` in Caddy,
  `proxy_buffering off` in nginx).

## The replication API

Peers pull over HTTP with a bearer token. Peer and site endpoints accept `https://` URLs, so you can
put the replication API behind TLS too. z3 doesn't do mutual TLS between nodes: use a private network
or VPN, or a TLS proxy, between sites.

```nginx
server {
    listen 9443 ssl;
    server_name peer.example.com;
    ssl_certificate     /etc/ssl/peer.example.com/fullchain.pem;
    ssl_certificate_key /etc/ssl/peer.example.com/privkey.pem;

    client_max_body_size 0;
    proxy_buffering off;

    location / {
        proxy_pass http://127.0.0.1:9002;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $http_host;
        # Log requests are held open for up to 20 seconds.
        proxy_read_timeout 120s;
    }
}
```

Then use `https://peer.example.com:9443` as this node's endpoint on the other nodes. See
[Bucket replication](/replication/bucket-replication).

## Sign-in with OpenID Connect

The OIDC callback is `/api/auth/oidc/callback` on the console. z3 builds it from the request's
`Host` and `X-Forwarded-Proto` headers, so with the proxy above it becomes
`https://console.example.com/api/auth/oidc/callback`. If your proxy rewrites those headers, set the
redirect URL explicitly in the OpenID Connect settings. See
[OpenID Connect and LDAP](/access/openid-connect-ldap).

## Clients

Point clients at the proxy's HTTPS address:

```bash
aws --endpoint-url https://s3.example.com s3 ls
```

Presigned URLs are signed for the host they're created with, so create them with the public
endpoint. See [Clients](/get-started/clients).
