---
title: "Upgrading"
description: "Back up, replace the binary or image, and restart. Metadata upgrades run automatically; upgrade every node of a replication group together."
---

An upgrade is: back up, replace the binary or image, restart. When Zee3 opens a data directory written
by an older version, it upgrades the metadata format in one transaction before it starts serving.

<Warning>
  Metadata upgrades are **one way**. An older Zee3 refuses a data directory that a newer one has
  upgraded, with `data directory uses format N, newer than this zee3 supports`. To go back, restore the
  backup you took before upgrading.
</Warning>

## Before you upgrade

1. Read the release notes in the [changelog](/changelog) and on
   [GitHub releases](https://github.com/terrific-ci/z3/releases).
2. Back up the data directory (below).
3. Check the node is healthy: the console's **Support** page or `zee3 admin support health`. Upgrading
   while disks are offline or healing is behind only adds to the work after the restart.

## Back up

Stop Zee3 so the files are consistent, then copy `ZEE3_DATA_DIR`. It holds the metadata (`meta.redb`),
the historical metrics (`metrics.redb`) and, on a node without separate disks, the chunks.

```bash
sudo systemctl stop zee3
sudo tar -C /var/lib -czf /backup/zee3-data-$(date +%F).tar.gz zee3
sudo systemctl start zee3
```

With Docker, copy the volume while the container is stopped:

```bash
docker compose stop zee3
docker run --rm -v zee3-data:/data -v "$PWD":/backup alpine \
  tar -czf /backup/zee3-data-$(date +%F).tar.gz -C /data .
docker compose start zee3
```

On a node with separate disks (`ZEE3_DISKS`, `ZEE3_POOLS`), the data directory holds only the metadata;
the chunks stay on the disks. That backup is what a rollback right after the upgrade needs. Restoring
it later loses every version written since the backup on that node (a replicated node gets them back
from its peers), so roll back soon or not at all.

Keep a [configuration export](/operations/config-export) as well: it's small and restores buckets,
IAM and settings on any node.

## Docker

```bash
docker compose pull
docker compose up -d
docker compose logs -f zee3
```

Pin a version tag (`terrificci/z3:1.0.1`) instead of `latest` to choose when you upgrade.

## Install script or systemd

Run the install script again, then restart the service:

```bash
curl -fsSL https://raw.githubusercontent.com/terrific-ci/z3/main/install.sh | sh
sudo systemctl restart zee3
```

Add `-s -- --version X` to install a specific version. The settings file `/etc/zee3/zee3.env` is kept.

## After the restart

```bash
zee3 --version
journalctl -u zee3 -n 50          # or: docker compose logs --tail 50 zee3
```

The log shows `upgrading metadata from format ...` when a format upgrade ran, then `storage ready`
and the addresses it listens on. Check the console's **Support** page once more.

## Replication groups

Nodes that replicate with each other should run the **same Zee3 version**: the replication protocol
can change with the metadata format. Upgrade them together, one after another, in a quiet period.
Writes keep working on the nodes that are up, and replication catches up from the change log once a
node is back.

The health check's **Peers and clocks** item warns when a peer runs a different version.

## Cluster members

Restart [cluster](/deploy/cluster) members one at a time, and wait until `zee3 admin cluster status`
shows the restarted member caught up before the next. Reads and writes continue on the others.

Replication on a cluster (peers, bucket and site replication, geo erasure coding) adds commands to
the Raft log that older members can't read. Upgrade every member first, then configure replication
on the cluster. A member still on the old version stops following the log when the first new command
arrives, and catches up once it is upgraded. Older single-node peers keep replicating with the
cluster, but give them one URL or a VIP instead of a comma-separated list.

[Erasure coding across members](/deploy/cluster#erasure-coding-across-members) adds Raft commands
too. Upgrade every member before you run `zee3 admin cluster ec`: a member on an older version stops
following the log when the layout is set, until it is upgraded. The on-disk format doesn't change,
and chunks stored as copies stay readable by every version.

## From 1.1.0 to 1.1.1

<Warning>
  1.1.1 cannot use a data directory written by an earlier version. The keys that protect IAM secrets,
  KMS keys and encrypted objects now carry the Zee3 name, so what 1.1.0 and 1.0.x stored can no
  longer be opened, and cluster members place erasure-coded shards differently.
</Warning>

Start 1.1.1 with an empty data directory, copy the objects over with the
[import](/deploy/migrate-from-minio) from the old node (it reads any S3 store), then create users,
access keys and KMS keys again. Upgrade every node of a replication group and every member of a
cluster together.

## From 1.0.x to 1.1.0

1.1.0 renames z3 to Zee3. The metadata format does not change, so the data directory is used as it
is, but names around it do:

| Before (1.0.x) | From 1.1.0 |
| --- | --- |
| Binary and command line `z3`, `z3 admin` | `zee3`, `zee3 admin` |
| Environment variables `Z3_*` | `ZEE3_*` (for example `ZEE3_DATA_DIR`, `ZEE3_ACCESS_KEY`) |
| Default credentials `z3admin` / `z3admin-secret` | `zee3admin` / `zee3admin-secret` |
| Metrics `z3_*` | `zee3_*` |
| Headers `x-z3-*` (such as `x-z3-session`) | `x-zee3-*` |
| Event destination ARNs `arn:z3:sqs::...` | `arn:zee3:sqs::...` (MinIO's `arn:minio:sqs::...` still works) |
| Configuration exports with `"z3_config"` | `"zee3_config"` |

<Steps>
  <Step title="Rename the settings">
    In the environment file, systemd unit or Compose file, rename every `Z3_` variable to `ZEE3_`.
    Keep `ZEE3_DATA_DIR` pointing at the existing data directory (or move the directory and point it
    there). Change the credentials if you relied on the defaults.
  </Step>
  <Step title="Upgrade every node together">
    Stop every node of a replication group and every member of a cluster, install 1.1.0, then start
    them. Nodes on 1.0.x and 1.1.0 use different header names between them, so they do not replicate
    with each other. With the install script, 1.1.0 installs a binary named `zee3`; the Docker image
    keeps its name, `terrificci/z3`.
  </Step>
  <Step title="Update what talks to Zee3">
    Dashboards and alerts that use `z3_*` metrics, clients that send `x-z3-session`, bucket
    notification configurations that name `arn:z3:` ARNs, and scripts that call `z3 admin`.
  </Step>
  <Step title="Take a new configuration export">
    Exports taken from 1.0.x do not import into 1.1.0. Temporary STS credentials issued before the
    upgrade stop working; ask for new ones.
  </Step>
</Steps>

## From 1.0.0 to 1.0.1

Replace the binary or the image and restart. The metadata format is unchanged, and 1.0.0 and 1.0.1
nodes can replicate with each other while you upgrade one after another.

## From 0.1.0 to 1.0.0

- The metadata format moves from version 6 to 7 when the node starts (the deletion-protection trash
  and the restore entry in the change log). Nothing is rewritten, but 0.1.0 cannot open the data
  directory afterwards.
- Upgrade every node of a replication group: 1.0.0 adds peer messages (restores, the replication
  map) that 0.1.0 does not know.
- New settings are off until you turn them on: cluster mode, deletion delays, `on_offline`.

## Downgrading

Stop Zee3, restore the data directory from the backup taken before the upgrade, install the old version
and start it.
