description: "How fast Zee3 1.0.0 stores and serves objects compared with MinIO and RustFS on the same machine, how much memory each uses, and how to measure it yourself."
---

Zee3 was measured against MinIO and RustFS with [warp](https://github.com/minio/warp), MinIO's S3
benchmark tool, on one machine, one server at a time, with the same limits and workloads.

## Setup

- **Machine:** a KVM virtual machine with 4 CPUs (Intel Xeon Silver 4114, 2.2 GHz), x86_64, 15 GiB
  of memory, Linux 7.0, one ext4 disk, nothing else running.
- **Limits:** every server ran in Docker on CPUs 0–1 with 2 GiB of memory and its data on the same
  disk (one drive each: Zee3 with a plain data directory, MinIO and RustFS in single-drive mode).
  warp ran on CPUs 2–3.
- **Versions:** Zee3 1.0.0 (`terrificci/z3:1.0.0`), MinIO RELEASE.2026-08-04 (the community build
  `pgsty/minio`; MinIO no longer publishes images), RustFS 1.0.6 (`rustfs/rustfs`), warp 1.3.1.
- **Settings:** each server's defaults. The objects are random data, so Zee3's deduplication and
  compression play no part.
- **Workloads:** 40 seconds each (stat 30 s), 1 MiB objects with 16 clients and 16 KiB objects
  with 32 clients. Every workload ran twice, on 2026-11-18; the tables show the average of both
  rounds. Zee3's rounds differed by less than 2% and RustFS's by less than 7%; MinIO varied more
  (GET 1 MiB 1,137 and 1,393 MiB/s, GET 16 KiB 3,038 and 3,675 objects/s).

## Results

| Workload | Zee3 | MinIO | RustFS |
|---|---|---|---|
| PUT 1 MiB | **150.7 MiB/s** | 124.4 MiB/s | 102.2 MiB/s |
| GET 1 MiB | **1,486 MiB/s** | 1,265 MiB/s | 609 MiB/s |
| PUT 16 KiB | 796 objects/s | 732 objects/s | **886 objects/s** |
| GET 16 KiB | **5,759 objects/s** | 3,357 objects/s | 5,439 objects/s |
| Mixed 1 MiB: GET | **309 MiB/s** | 223 MiB/s | 177 MiB/s |
| Mixed 1 MiB: PUT | **102.9 MiB/s** | 74.3 MiB/s | 58.8 MiB/s |
| HEAD (stat) 16 KiB | **10,068 objects/s** | 3,663 objects/s | 7,839 objects/s |
| Peak memory | **174 MiB** | 997 MiB | 284 MiB |

Mixed is warp's default mix of GET, PUT, STAT and DELETE on the same objects, so its rows show the
GET and PUT throughput within it. Peak memory is the highest container memory seen after any
workload.

- **Large objects:** Zee3 writes 1 MiB objects 21% faster than MinIO and 47% faster than RustFS,
  and reads them 17% faster than MinIO and more than twice as fast as RustFS.
- **Small objects:** RustFS takes small writes fastest, 11% ahead of Zee3; Zee3 reads small objects
  and answers HEAD requests fastest.
- **Memory:** Zee3 stays under 180 MiB through every workload, less than a fifth of MinIO.

Zee3 1.0.0 matches 0.1.0 on every workload (within 2%). Uploads now write several chunks at once and
downloads read ahead, which made no difference on this machine, where the drive sets the upload
limit; both help on faster drives and more cores.

<Note>
  This is a single-drive setup on one machine. Erasure-coded disk sets, several nodes and replication
  change the picture for every server; measure the layout you plan to run.
</Note>

## Footprint on a shared machine

`bench/footprint.sh` runs each server with no CPU or memory limits, as on a machine shared with
other services, and measures CPU while idle, CPU per object while writing 4 KiB objects, and the
process's own memory (anonymous, without the page cache) as objects pile up.

| | Zee3 | MinIO | RustFS |
|---|---|---|---|
| Idle CPU, empty | 0.2% of a core | 0.1% | 0.2% |
| Idle CPU after ~200,000 objects | **0.26%** | 17% | 15–17% |
| CPU per object while writing | 1.8 ms | 1.6 ms | 1.8 ms |
| Memory at start | **2 MiB** | 66 MiB | 22 MiB |
| Memory at ~200,000 objects | **~105 MiB** (1.0.1, `ZEE3_META_CACHE_MB=64`) | 287 MiB | 196 MiB (still growing) |
| OS page cache (reclaimable) | **227 MiB** | 2,678 MiB | 1,852 MiB |

- MinIO and RustFS keep scanning their data in the background (about 17% of a core). Zee3 is quiet
  when nothing asks it for anything.
- Zee3's memory follows its metadata cache. Since 1.0.1 it is capped by `ZEE3_META_CACHE_MB` (128 MiB by
  default, so about 160 MiB in all). With 64 MiB it levels off near 100 MiB and writes are just as
  fast, since the operating system still caches the metadata file. See
  [Running alongside other services](/deploy/shared-host).

## Measure it yourself

The script runs the three servers one after another with the same limits and prints one line per
workload, with the throughput and the container's memory:

```bash
curl -fsSLO https://raw.githubusercontent.com/terrific-ci/z3/main/bench/run.sh
chmod +x run.sh
./run.sh 1          # results in results-1.txt
```

It needs Docker and a machine with at least 4 CPUs. Data goes to `/var/tmp/s3bench-data` and is
removed afterwards; warp also deletes its objects after each workload. Set `ZEE3_IMAGE` to measure
another Zee3 image.
