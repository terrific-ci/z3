description: "Admin API endpoints for peers, per-bucket replication, conflicts, link status, anti-entropy, site replication, the peer token, first-run setup and joining new nodes."
---

These endpoints set up and watch [replication](/replication/overview). Reading needs
`admin:ServerInfo`; changing needs `admin:ConfigUpdate`.

Replication itself runs between nodes on the **peer API** (port 9002), which needs a peer token
(`ZEE3_PEER_TOKEN`, or [set in the console](/replication/site-replication#peer-token-from-the-console)) on the node being pulled from. The
endpoints below are on the admin API.

On a [cluster](/deploy/cluster#replication-with-other-zee3-nodes), call them on any member: peers and
replication settings are stored in the cluster's metadata, and every member answers the same.

## Endpoints

| Method | Path | Description |
| --- | --- | --- |
| `GET` | `/api/peers` | Peers (tokens hidden) |
| `PUT` | `/api/peers/{name}` | Add or change a peer |

| `GET` | `/api/buckets/{bucket}/replication` | A bucket's replication |
| `PUT` | `/api/buckets/{bucket}/replication` | Set a bucket's replication (empty `peers` turns it off) |
| `POST` | `/api/buckets/{bucket}/replication/resync` | Run Merkle anti-entropy against each peer now (on a cluster follower, it runs on the leader) |
| `GET` | `/api/buckets/{bucket}/conflicts` | Concurrent writes resolved by HLC |
| `GET` | `/api/replication` | Live state of every link |
| `GET` | `/api/replication?view=peers` | Per peer: online or offline, last contact, changes waiting to send and to receive ([Edge](/replication/edge#monitoring)) |
| `GET` | `/api/replication/topology` | Every node's links, peers, site and bucket settings, gathered from the whole group ([Replication map](/replication/map#api)) |
| `GET` | `/api/changelog/pruning` | [Change-log pruning](/replication/overview#change-log-pruning): retention and the last pass per bucket |

| `DELETE` | `/api/site` | Leave site replication (this node only) |
| `GET` | `/api/node/peer` | [This node's peer token](#peer-token): token source, listening state (the token for root) |

| `POST` | `/api/join/requests/{id}/deny` | Deny a join request (root) |
| `POST` | `/api/join/requests/{id}/retry` | Reach an approved new node again, optionally at another address (root) |
| `GET` | `/api/join/status` | On a node that joined at setup: how its join goes |

## Peers

A peer is another Zee3 node this node pulls changes from.

`PUT /api/peers/{name}`:

<ParamField body="endpoint" type="string" required>
  The peer's replication API, like `http://10.0.0.2:9002` or `https://dc2.example.com:9002`.
  An `https://` peer is called with this node's certificate when
  [mutual TLS](/deploy/peer-tls) is on. Several URLs separated by commas, like the members of a
  cluster (`http://10.0.0.11:9002,http://10.0.0.12:9002`), are tried in turn: the URL that last
  answered is used, and the next one on a connection error or a 503. Each URL must start with
  `http://` or `https://`.
</ParamField>

<ParamField body="token" type="string" required>
  The peer's token (its `ZEE3_PEER_TOKEN`, or the one set in its console). When changing an existing peer, an empty token keeps the saved one.
</ParamField>

<ParamField body="max_bytes_per_sec" type="integer">
  Throttle chunk transfers from this peer, all buckets together. Must be positive.
</ParamField>

<ParamField body="windows" type="string[]">
  UTC time windows when replication from this peer runs, like `["22:00-06:00"]`. Empty: always.
</ParamField>

```bash
curl -X PUT http://127.0.0.1:9001/api/peers/dc2 -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"endpoint": "https://dc2.example.com:9002", "token": "peer-token-of-dc2", "windows": ["22:00-06:00"]}'
```

`GET /api/peers`:

```json
[ { "name": "dc2", "endpoint": "https://dc2.example.com:9002", "node_id": "01a1e327-...", "token": "***",
    "max_bytes_per_sec": null, "windows": ["22:00-06:00"] } ]
```

`node_id` is learned on first contact.

## Bucket replication

`PUT /api/buckets/{bucket}/replication`:

```json
{
  "peers": ["dc2", "dc3"],
  "mode": { "quorum": 1 },
  "timeout_ms": 5000,
  "priority": "high",
  "rules": [
    { "prefix": "tmp/", "replicate": false },
    { "prefix": "records/", "mode": "all" },
    { "prefix": "eu/", "sites": ["fra"] }
  ],
  "geo": null
}
```

| Field | Default | Meaning |
| --- | --- | --- |
| `peers` | | Peer names to replicate with. Empty turns replication off |
| `mode` | `"async"` | When a write answers: `"async"` after the local commit, `{"quorum": N}` once N peers applied it, `"all"` once every peer did |
| `timeout_ms` | `5000` | How long a `quorum` or `all` write waits before failing with `503` |
| `priority` | `"normal"` | `"high"`, `"normal"` or `"low"`: bandwidth priority when a peer is throttled |
| `rules` | `[]` | Checked in order; the first that matches a key decides |
| `geo` | `null` | Geo erasure coding for new writes: `{"data": 2, "parity": 1}` ([Geo erasure coding](/replication/geo-erasure-coding)) |
| `on_offline` | `"wait"` | For `quorum`/`all`: `"wait"` for the timeout, or `"local"` to answer at once while the peers needed are offline ([Edge](/replication/edge#on_offline)) |

A rule:

| Field | Meaning |
| --- | --- |
| `prefix` | Keys starting with this (empty: every key) |
| `tags` | Objects with all of these tags. Never matches removals, which have no tags |
| `replicate` | `false` keeps matching objects on this node only (default `true`) |
| `mode` | Overrides the bucket's mode for matching keys |
| `sites` | Data residency: only these sites (or peers) may hold matching objects. Writes elsewhere are refused |

`GET` answers the same shape, plus `managed` (`true` when site replication manages the bucket) and
`updated` (when it last changed). See [Bucket replication](/replication/bucket-replication).

### Resync

`POST /api/buckets/{bucket}/replication/resync` compares the bucket with each peer through Merkle
trees and repairs what differs, without waiting for the next anti-entropy run. On a cluster, a
follower runs it on the leader, where the links run:

```json
[ { "peer": "dc2", "divergent_leaves": 3, "repaired": 12 } ]
```

### Conflicts

`GET /api/buckets/{bucket}/conflicts?limit=50` (at most 1000) lists concurrent writes to the same key
from different nodes. Both versions are kept; the one with the higher HLC is current everywhere.

```json
[
  { "key": "reports/q3.pdf", "detected": { "physical_ms": 1794921008881, "logical": 0 },
    "winner_version": "01a1e9a1-0ef1-7489-8fd7-60050032d518", "winner_origin": "01a1e9a0-...", "winner_hlc": { "physical_ms": 1794921008700, "logical": 0 },
    "loser_version": "01a1e9a1-0dd2-7c41-a2b8-f0e5c3d91a77", "loser_origin": "01a1e327-...", "loser_hlc": { "physical_ms": 1794921008650, "logical": 0 } }
]
```

## Link status

`GET /api/replication` answers one entry per (peer, bucket) link:

```json
[
  {
    "peer": "dc2", "bucket": "radiology", "state": "streaming", "peer_node_id": "01a1e327-...",
    "cursor": 18233, "remote_head": 18233, "lag_entries": 0, "lag_ms": 0, "last_delay_ms": 84,
    "applied": 18233, "skipped": 0, "conflicts": 1, "chunks_fetched": 20411,
    "bytes_raw": 61203394112, "bytes_wire": 40211993002, "bytes_deduplicated": 1204332110,
    "last_sync_ms": 1794921008881, "errors": 0, "last_error": null,
    "anti_entropy_runs": 288, "last_anti_entropy_ms": 1794920700000, "last_divergent_leaves": 0,
    "anti_entropy_repaired": 4, "throttled_ms": 0, "geo_chunks": 0
  }
]
```

| Field | Meaning |
| --- | --- |
| `state` | `connecting`, `streaming`, `error`, or `paused` (outside the peer's windows) |
| `worker` | On a [cluster](/deploy/cluster#monitoring): the member running the link (the leader). Every member shows each link once. Absent on a single node |
| `cursor`, `remote_head` | The last peer log entry applied here, and the peer's newest |
| `lag_entries`, `lag_ms` | Entries not applied yet, and the age of the oldest (0 when caught up) |
| `last_delay_ms` | From the origin's commit to the local apply, for the last change |
| `bytes_wire`, `bytes_raw`, `bytes_deduplicated` | Bytes over the network, chunk bytes stored after decompression, chunk bytes not sent because they were already here |
| `throttled_ms` | Time spent waiting for the peer's bandwidth limit |
| `geo_chunks` | Geo-erasure-coded chunks for which only this site's shards were fetched |
| `last_contact_ms`, `offline`, `offline_since_ms` | When the peer last answered, and whether it counts as offline (no answer for 10 s on any link) |
| `outgoing_entries` | Changes made here that the peer has not pulled yet |

`GET /api/replication?view=peers` carries the same `worker` on each peer.

The same figures feed the `zee3_replication_*` [Prometheus metrics](/operations/prometheus#replication).

## Site replication

Site replication replicates every bucket of every site, and keeps bucket creation, deletion,
versioning, replication settings, IAM and the other cluster documents in step. See
[Site replication](/replication/site-replication).

`PUT /api/site` sets it up on this node and then hands the same configuration to every other site,
authenticating with that site's token, so **one call sets up the whole group**:

```json
{
  "name": "jkt",
  "sites": {
    "jkt": { "endpoint": "https://jkt.example.com:9002", "token": "token-of-jkt" },
    "sby": { "endpoint": "https://sby.example.com:9002", "token": "token-of-sby", "max_bytes_per_sec": 104857600 },
    "bdg": { "endpoint": "https://bdg.example.com:9002", "token": "token-of-bdg", "windows": ["22:00-06:00"] }
  },
  "topology": "mesh"
}
```

| Field | Meaning |
| --- | --- |
| `name` | This node's own site, one of the keys of `sites` |
| `sites` | Every site (at least two): its replication API `endpoint` (several URLs separated by commas for a cluster's members), its peer token, and optionally `max_bytes_per_sec` and `windows` for pulling from it |
| `topology` | `"mesh"` (every site pulls from every other), `{"hub_spoke": {"hub": "jkt"}}`, or `{"chain": {"order": ["jkt", "sby", "bdg"]}}` (each site pulls from its neighbours). Changes are relayed, so every topology reaches every site |

The answer says how the push to each other site went:

```json
[ { "site": "sby", "ok": true }, { "site": "bdg", "ok": false, "error": "error sending request ..." } ]
```

`GET /api/site` answers the configuration with tokens as `***`, or `null`. `DELETE /api/site` makes
this node leave; the other sites keep their configuration.

## Peer token

`GET /api/node/peer` (`admin:ServerInfo`) describes the peer API of the node you call:

```json
{
  "source": "console", "configured": true, "token": "3f9c...", "listening": true, "error": null,
  "addr": "0.0.0.0:9002", "scheme": "http", "cluster_needs_restart": false, "can_change": true,
  "name": "jakarta", "endpoint": "https://peer-a.example.com"
}
```

| Field | Meaning |
| --- | --- |
| `source` | Where the token comes from: `env` (`ZEE3_PEER_TOKEN`), `console`, or `none` |
| `configured` | Whether there is a token |
| `token` | The token, for root only (`null` for everyone else) |
| `listening`, `error` | Whether the peer API listens, and why not when it failed to start |
| `addr`, `scheme` | Its address (`ZEE3_PEER_ADDR`) and `http` or `https` ([peer TLS](/deploy/peer-tls)) |
| `cluster_needs_restart` | The token was set in the console after start: restart before joining a [cluster](/deploy/cluster), which reads it only at start |
| `can_change` | Whether `PUT` may change it: root, a token not from `ZEE3_PEER_TOKEN`, and not a cluster member |
| `name` | The name other nodes know this node by (its site name) |
| `endpoint` | This node's replication address saved in the console, or `null` |

`PUT /api/node/peer` (root) sets a token, at least 16 characters without spaces, or generates one:

```bash
curl -X PUT http://127.0.0.1:9001/api/node/peer -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{"generate": true}'
```

```json
{ "token": "9b1e...", "sites": [ { "site": "sby", "ok": true }, { "site": "bdg", "ok": false, "error": "..." } ] }
```

The peer API starts without a restart if it was off, and a changed token applies in place. The token
is kept in `<data dir>/credentials.json`. When this node is in a site group, the group with the new
token is pushed to every other site; `sites` says how each push went. Peers configured by hand on
other nodes must be changed there. A token from `ZEE3_PEER_TOKEN` is refused (change the variable and
restart), and so is any change on a cluster member (`409`): members share one `ZEE3_PEER_TOKEN`.

`{"endpoint": "https://peer-a.example.com"}` saves this node's replication address (`""` clears it),
also with a token from `ZEE3_PEER_TOKEN`. Like a new token, it is written into this node's entry of
its site group and pushed to every other site. In `PUT /api/site`, a site whose `token` is empty
keeps the token the group already has for it (this node's own: its peer token).

## First-run setup

A node with a new data directory and no root credentials serves only these on its admin port until
setup is done (every other `/api/` route answers `503`, except `GET /api/health`). See
[Root credentials](/deploy/configuration#root-credentials) and
[Join from the setup page](/replication/site-replication#join-from-the-setup-page).

| Method | Path | Description |
| --- | --- | --- |
| `GET` | `/api/setup` | `{"product": "zee3", "needed": true, "version", "name", "node"}`. Also answered once set up, with `needed: false` |
| `POST` | `/api/setup` | `{"access_key", "secret_key"}`: finish setup as a new node |
| `POST` | `/api/setup/discover` | Start looking for Zee3 nodes on the network: `{"id"}` |
| `GET` | `/api/setup/discover/{id}` | `{"probed", "total", "done", "networks", "found": [{"url", "name", "node", "version", "via"}]}`; `via` is `mdns` or `scan` |
| `POST` | `/api/setup/pairing` | `{"url", "endpoint"?}`: ask the console at `url` to join; answers `{"id", "code", "site"}` with the six-digit code to approve there |
| `GET` | `/api/setup/pairing/{id}` | `{"status", "code", "site", "error"}`; `status` is `waiting`, `approved`, `joined`, `denied`, `expired` or `failed`. On `joined`, setup is done |
| `POST` | `/api/setup/join` | `{"join_code", "endpoint"?}`: join with a `zee3-join:` code, no approval |

`endpoint` is this node's replication address as the existing node reaches it, such as
`http://203.0.113.9:9002`. Without it, the existing node uses the address the request came from with
this node's peer port.

## Join requests

The existing node's side of joining. These are public, for the new node's setup page:

| Method | Path | Body or header |
| --- | --- | --- |
| `POST` | `/api/join/requests` | `{"code", "nonce", "name", "token", "peer_port", "scheme", "endpoint"?}`: a pairing request; answers `{"id", "site"}` |
| `GET` | `/api/join/requests/{id}` | Header `x-zee3-join-nonce` with the request's nonce: `{"status", "error", "bootstrap", "endpoint", "site"}`. `bootstrap` (root credentials, the group, and the request id and nonce to follow it) is only there once approved |
| `POST` | `/api/join/code` | The secret of a join code with the same fields: joins at once |

At most 32 requests wait at a time, and each expires after ten minutes.

For admins:

- `GET /api/join/pending` (`admin:ServerInfo`) lists the requests of the last ten minutes, newest
  first: `id`, `code`, `name`, `from` (the address it came from), `version`, `created_ms`, `status`,
  `error`, `member` (its site name once approved) and `endpoint` (where this node reaches the new
  node's peer API). Approved requests stay while this node tries, failed ones for a day.
- `POST /api/join/requests/{id}/approve` (root) hands the new node the root credentials and answers
  `{"member": "<site name>"}`. Once the new node's peer API answers, this node adds it to the site
  group (making one if there is none) and pushes the configuration to every site. If this node had
  no peer token, one is generated and its peer API turned on.
- `POST /api/join/requests/{id}/deny` (root).
- `POST /api/join/requests/{id}/retry` (root) with `{"endpoint"?}`: for an approved request that has
  not joined (still trying, or failed), try again for ten minutes, at `endpoint` when given. Answers
  `{"endpoint"}`.
- `GET /api/join/status` on the new node (signed in) asks the node it joined at setup:
  `{"status", "site", "name", "api", "since_ms", "endpoint", "error"}` with `status` `approved`
  (still being reached at `endpoint`), `failed`, `lost` (that node no longer knows the request),
  `unreachable`, or `none` once it is in the group.
- `POST /api/join/codes` (root) with `{"api": "<this console's URL as the new node reaches it>"}`
  answers `{"code": "zee3-join:...", "expires_ms"}`. A code works once, for one hour, and is
  forgotten when this node restarts.
