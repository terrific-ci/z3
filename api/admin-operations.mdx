These endpoints run and watch a node. Reading needs `admin:ServerInfo`; changing needs
`admin:ConfigUpdate`, unless noted.

## Info

`GET /api/info`:

```json
{
  "version": "0.1.0", "uptime_secs": 86400, "node_id": "01a1e9a0-be79-7462-83e2-8685ea015598",
  "buckets": 12, "objects": 1204331, "logical_bytes": 2309011234511, "physical_bytes": 1840223344012,
  "chunks": 2203114, "multipart_uploads": 3, "dedup_ratio": 1.2547
}
```

`logical_bytes` counts every version as clients see it; `physical_bytes` what the chunk store
references after deduplication. `dedup_ratio` is their quotient.

## Status

`GET /api/status` returns the [Running status](/operations/running-status#api): version, node id,
uptime, `host` (name, OS, CPUs, load, memory), `totals` since start, and `history`, one sample every
`sample_secs` (5) for the last hour.

## Metrics

`GET /api/metrics?range=24h[&bucket=name]` returns a series from the [historical metrics](/operations/metrics).

<ParamField query="range" type="string" default="24h">
  A number and `m`, `h`, `d`, `w` or `y`: `90m`, `24h`, `7d`, `1y`. From 1 minute to 3 years.
</ParamField>

<ParamField query="bucket" type="string">
  One bucket instead of the node.
</ParamField>

```json
{
  "range_secs": 86400, "tier": "minute", "step_secs": 480, "from": 1794834600,
  "points": [
    null,
    { "t": 1794835080, "requests": 9120, "reads": 8011, "writes": 1109, "errors": 4, "client_errors": 4,
      "server_errors": 0, "bytes_in": 120433221, "bytes_out": 904331221, "cpu_percent": 12.4,
      "process_memory": 335724544, "memory_used": 19275776000, "buckets": 12, "objects": 1204331,
      "logical_bytes": 2309011234511, "physical_bytes": 1840223344012 }
  ]
}
```

- `tier` is `minute`, `hour` or `day`; `step_secs` the length of one point; `from` the start of the
  first point (Unix seconds). There are at most 180 points.
- A point is `null` for a period with no data (the node was down).
- With `bucket`, a point has `t`, `requests`, `errors`, `bytes_in`, `bytes_out`, `objects` and `bytes`.

`GET /api/metrics/buckets?range=24h` lists every bucket, busiest first:

```json
{ "range_secs": 86400, "buckets": [
  { "bucket": "radiology", "requests": 912044, "errors": 120, "bytes_in": 6020334411, "bytes_out": 30140332211,
    "objects": 812004, "bytes": 1759218604441 } ] }
```

Traffic is over the range; `objects` and `bytes` are the size now. A bad range answers `400`.

## Support

See [Support tools](/operations/support) for what each tool does.

### Health

`GET /api/support/health`:

```json
{
  "generated_ms": 1794921056000, "version": "0.1.0", "node_id": "01a1e9a0-be79-7462-83e2-8685ea015598",
  "uptime_secs": 86400, "level": "warn",
  "host": { "hostname": "zee3-jkt-1", "cpus": 16, "...": "..." },
  "checks": [
    { "id": "disks", "title": "Disks", "level": "ok", "summary": "6 disks online", "details": { "...": "..." } },
    { "id": "credentials", "title": "Root credentials", "level": "warn",
      "summary": "Root still uses the default access and secret key; set ZEE3_ACCESS_KEY and ZEE3_SECRET_KEY", "details": {} }
  ]
}
```

Check ids: `disks`, `disk_latency`, `healing`, `peers`, `peer_tls`, `replication`, `resources`,
`errors`, `log_history`, `credentials`, `kms`, `trash`, `lean`. `level` is `ok`, `warn` or `fail`;
the report's level is the worst.

### Speed test

`POST /api/support/speedtest`:

<ParamField body="kind" type="string" required>
  `drive` or `network`.
</ParamField>

<ParamField body="size_mb" type="integer" default="64">
  Megabytes per disk or per peer, 1 to 1024.
</ParamField>

```json
{ "kind": "drive", "size_mb": 64,
  "results": [ { "index": 0, "path": "/mnt/d1", "write_mbps": 412.3, "read_mbps": 1830.1 } ],
  "total_write_mbps": 412.3, "total_read_mbps": 1830.1 }
```

For `network`, each result is `{"name", "rtt_ms", "bytes", "download_mbps"}` for a peer. A disk or
peer that fails has `error` instead.

### Profile

`POST /api/support/profile?seconds=15` (1 to 120) samples for that long, then answers a zip
(`application/zip`, named `zee3-profile-<time>.zip`) with `flamegraph.svg`, `cpu.pb`, `runtime.json`
and `README.txt`. Needs a Unix host.

```bash
curl -X POST -H "Authorization: Bearer $TOKEN" -o profile.zip \
  "http://127.0.0.1:9001/api/support/profile?seconds=30"
```

Only one speed test or profile runs at a time; a second one answers `409`.

### Inspect

`GET /api/support/inspect?bucket=photos&key=2026/a.jpg` answers a zip with `object.json`,
`layout.json`, `chunks/` and `README.txt`.

| Query | Meaning |
| --- | --- |
| `bucket`, `key` | Required |
| `version_id` | A version; default the current one |
| `data` | `false` leaves out the raw chunk files |

With data, the files may total at most 1 GiB; above that the answer is `413`.

## Cluster

`GET /api/cluster` answers the [cluster](/deploy/cluster) as this member sees it:

```json
{
  "enabled": true, "member_id": "5168186497781187492", "name": "zee3-2", "addr": "http://10.0.0.12:9002",
  "state": "Follower", "term": 3, "leader": "2200471768134479368", "leader_log": 1840,
  "last_log": 1840, "last_applied": 1840,
  "members": [
    { "id": "2200471768134479368", "name": "zee3-1", "addr": "http://10.0.0.11:9002", "version": "1.0.3",
      "voter": true, "leader": true, "me": false, "role": "leader", "matched": 1840,
      "chunks": { "at": 1794921000000, "shards": 24102, "shard_bytes": 11166914560, "copies": 3911,
                  "copy_bytes": 420688691, "rebuilt": 0, "converted": 1840, "failed": 0 } }
  ],
  "copies": 3, "copies_configured": 3, "consistent_reads": true,
  "layout": { "mode": "erasure", "data": 4, "parity": 2, "min_size": 262144, "write_quorum": 5, "fits": true },
  "redundancy": {
    "at": 1794921000000,
    "audit": { "copy_chunks": 7829, "ec_chunks": 24091, "degraded": 0, "at_risk": 0, "lost": 0, "at_risk_chunks": [] }
  },
  "sweep": { "at": 1794921000000, "report": { "...": "..." } },
  "replication_worker": "zee3-1"
}
```

- `role` is `leader`, `follower` or `leaving`; `matched` is the last log entry the member matches
  on the leader.
- `replication_worker` is the member running the
  [replication links](/deploy/cluster#replication-with-other-zee3-nodes) (the leader), or `null`
  outside a cluster or while there is no leader.
- `layout` is `{"mode": "copies"}`, or with
  [erasure coding across members](/deploy/cluster#erasure-coding-across-members)
  `{"mode": "erasure", ...}`: `data` and `parity` shards, `min_size` (smaller chunks stay copies),
  `write_quorum` (shards a write must store, `data + ceil(parity / 2)`) and `fits` (`false` while the
  cluster has fewer voting members than shards).
- A member's `chunks` comes from its last placement sweep: the shards and copies it holds with their
  bytes, plus `rebuilt`, `converted` and `failed` from that sweep. It is `null` until the member has
  run a sweep or when it doesn't answer.
- `redundancy` is the leader's last audit of erasure-coded chunks: `degraded` chunks miss at least
  one shard, `at_risk` chunks have `data` shards or fewer left, `lost` chunks have fewer than `data`
  and can't be read until members come back. `at_risk_chunks` lists up to 20 of them. It is `null`
  before the leader's first sweep.

The sweep report (`sweep.report` here and each member's `report` from `POST /api/cluster/sweep`)
has `checked`, `pulled`, `pushed`, `dropped`, `failed`, and with erasure coding `rebuilt` (shards
rebuilt from the others), `converted` (chunks moved to the current layout, on the leader),
`shards`, `shard_bytes`, `copies` and `copy_bytes`.

`PUT /api/cluster/ec` sets the layout for the whole cluster through any member and answers with the
new status:

```bash
curl -X PUT http://127.0.0.1:9001/api/cluster/ec -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{"layout": "4+2", "min_size": 262144}'
```

`layout` is `data+parity` (at least 2 data and 1 parity shard, at most 32 shards) or `off`.
`min_size` is optional (default `262144`). A bad layout, or one with more shards than voting
members (`4+2 needs at least 6 members, the cluster has 5`), answers `400` with the reason. The
leader then converts existing chunks in the background.

## Pools

`GET /api/pools`:

```json
{
  "pools": [
    { "index": 0, "id": "01a1e9a0-be6d-7121-a910-033f203a3778", "data": 2, "parity": 2, "writable": true,
      "disks": [ { "pool": 0, "index": 0, "path": "/mnt/a1", "state": "online", "total_bytes": 1000204886016, "free_bytes": 110223344123 } ],
      "total_bytes": 4000819544064, "free_bytes": 440893376492, "state": "active", "stored_bytes": 1539316278886 }
  ],
  "usage_measured_ms": 1794921000000,
  "op": {
    "kind": "rebalance", "state": "running", "started_ms": 1794920000000, "finished_ms": null,
    "created_by": "zee3admin", "pool_id": null, "pool_index": null,
    "dirs_done": 25, "dirs_total": 256, "passes": 1, "moved_chunks": 2412, "moved_bytes": 8912003311,
    "gone": 0, "failed": 0, "errors": [], "message": null, "...": "..."
  }
}
```

- A pool's `data` and `parity` are `null` for a plain directory. `state` is `active`, `draining` or
  `decommissioned`. `stored_bytes` is measured every minute.
- `op` is the current or last operation: `kind` `rebalance` or `decommission`, `state` `running`,
  `done`, `failed` or `cancelled`.

`POST /api/pools/rebalance` and `POST /api/pools/{index}/decommission` answer `202` with the new
operation, `400` when it cannot run (`rebalancing needs at least two active pools`), or `409` when
another one is running. `POST /api/pools/cancel` answers `204`, or `400` when nothing runs. See
[Pools](/durability/pools).

## Settings

`GET /api/settings`:

```json
{
  "subsystems": ["region", "api", "compression", "scanner", "logger", "webdav", "ftp", "sftp", "nfs"],
  "keys": [
    { "subsystem": "api", "key": "requests_max", "label": "Concurrent requests",
      "help": "S3 requests handled at once on this node; more wait for a free slot. 0: no limit.",
      "type": "int", "min": 0, "max": 100000, "unit": "", "default": 0, "env": null, "value": 500, "is_set": true }
  ]
}
```

`type` is `int` (with `min`, `max`, `unit`), `bool`, `text` (with a `format`: `region`, `address`,
`ports`, `path` or `name`), `list` or `filter`. `env` names the startup variable the default comes from.

`PUT /api/settings/{subsystem}` takes `{"key": value, ...}` for the keys to change; `null` puts a key
back to its default. The whole body is checked first, and a bad value answers `400` with the reason.
`DELETE /api/settings/{subsystem}` resets every key of the subsystem. Every key is listed in
[Cluster settings](/operations/settings).

```bash
curl -X PUT http://127.0.0.1:9001/api/settings/api -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{"requests_max": 500, "requests_deadline_secs": null}'
```

## Protocols

`GET /api/protocols` answers the state of each file protocol on this node:

```json
[
  { "name": "sftp", "enabled": true, "state": "running", "address": "0.0.0.0:8022", "error": null,
    "since_ms": 1794920996938, "sessions": 2, "logins": 41, "failed_logins": 3,
    "fingerprint": "SHA256:Ujlfbc1TnB+t9xW0WLl3qWtlu41h0SUQ60bQngnCiRc" }
]
```

`state` is `off`, `starting`, `running` or `failed` (with `error`). `fingerprint` is the SFTP host key's.
Protocols are turned on and configured with `PUT /api/settings/{webdav,ftp,sftp,nfs}`:

```bash
curl -X PUT http://127.0.0.1:9001/api/settings/sftp -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{"enabled": true, "address": "0.0.0.0:8022"}'
```

See [File protocols](/protocols/overview).

## Batch jobs

`POST /api/batch` takes a [job definition](/cli/batch#job-definitions) and answers `201` with the job.
It is checked first: the bucket exists, a remote target answers, the KMS key exists.

```json
{
  "id": "expire-146d75b7b7a2775c",
  "spec": { "type": "expire", "source": { "bucket": "logs", "prefix": "tmp/" }, "filter": { "older_than": "30d" },
            "versions": "all", "dry_run": true },
  "state": "done", "created_ms": 1794921010000, "finished_ms": 1794921011000, "created_by": "zee3admin",
  "progress": { "scanned": 3, "matched": 2, "done": 2, "skipped": 0, "failed": 0, "bytes": 400000 },
  "cursor": "tmp/b.log", "errors": [], "samples": ["tmp/a.log", "tmp/b.log"], "message": null
}
```

| Field | Meaning |
| --- | --- |
| `state` | `running`, `done`, `failed` or `cancelled` |
| `progress` | Versions scanned and matched; done, skipped, failed; bytes handled |
| `cursor` | The last key fully handled; a job interrupted by a restart continues after it |
| `errors` | Up to 20 recent errors |
| `samples` | Dry runs: up to 100 keys that would be touched |
| `message` | Why the job failed or stopped |

A replicate job's target secret key is stored sealed and never sent back. `POST /api/batch/{id}/cancel`
answers `400` for a job that is not running; `DELETE /api/batch/{id}` answers `400` for a running job
(cancel it first) and `404` for an unknown one. See [Batch jobs](/storage/batch).

### Point-in-time rollback

`POST /api/batch/rollback/preview` takes `{"source": {"bucket", "prefix"}, "key": null, "at": "<RFC 3339>", "limit": 100}`
and answers with the plan, changing nothing:

```json
{
  "bucket": "records", "at_ms": 1794958373946, "from_seq": 1501, "until_seq": 3002,
  "counts": { "log_entries": 1502, "keys": 10, "restore": 4, "delete": 4, "missing": 1, "unchanged": 1, "from_trash": 0 },
  "changes": [
    { "key": "patients/del.txt", "action": "restore", "version_id": "01a1ebdb32ad74bebf1338785669667b" },
    { "key": "patients/new1.txt", "action": "delete" },
    { "key": "patients/purged.txt", "action": "missing", "reason": "the version current at that time was deleted since" }
  ]
}
```

`from_seq` and `until_seq` are the part of the bucket's change log that was read. `from_trash` counts
restores whose version comes back from the [trash](/storage/deletion-protection) (their `reason` is
`from the trash`). A bucket that never had versioning, or has it suspended, answers `400`.

To run it, `POST /api/batch` with `{"type": "rollback", "source": {...}, "key": null, "at": "..."}`; a
time in the future answers `400`. A rollback job carries `rollback` with the same counts, and its
`samples` list its changes. See [Point-in-time rollback](/storage/point-in-time).

## Disks, healing and garbage collection

`GET /api/disks`:

```json
{
  "erasure": { "data": 4, "parity": 2 },
  "disks": [
    { "pool": 0, "index": 0, "path": "/mnt/d1", "state": "online", "total_bytes": 1000204886016, "free_bytes": 400123344121 },
    { "pool": 0, "index": 3, "path": "/mnt/d4", "state": "offline", "reason": "No such file or directory (os error 2)",
      "total_bytes": null, "free_bytes": null }
  ],
  "healing": { "chunks_checked": 2203114, "shards_repaired": 12, "chunks_lost": 0, "lost_now": 0, "full_scans": 3,
               "last_full_scan_ms": 1794834588308, "last_full_scan": { "checked": 2203114, "damaged": 4, "repaired": 12, "lost": 0, "lost_chunks": [] },
               "geo_passes": 5, "geo_shards_repaired": 3, "geo_chunks_failed": 0, "geo_unrepairable": 0, "geo_skipped": 0,
               "last_geo_pass_ms": 1794834590120, "last_geo_pass": { "checked": 81220, "damaged": 3, "repaired": 3, "failed": 0,
                                                                      "skipped": 0, "failed_chunks": [], "errors": [] } },
  "orphan_sweep": { "runs": 3, "chunks_deleted": 14, "bytes_freed": 58720256, "last_run_ms": 1794834601120,
                    "last": { "dry_run": false, "dirs": 4096, "chunks_checked": 2203128, "orphans": 14, "young": 0,
                              "deleted": 14, "bytes_freed": 58720256, "tmp_files": 1, "tmp_bytes": 4194304, "duration_ms": 41200 } }
}
```

`erasure` is `null` for a single data directory. A disk's `state` is `online`, `offline` or `foreign`
(it holds another set's data and is never written), with a `reason` for the last two.

In `healing`, `chunks_lost` counts every lost chunk found since the start, and `lost_now` the ones
not repaired since (the health check uses `lost_now`). The `geo_` totals are for
[rebuilding geo shards from other sites](/replication/geo-erasure-coding#healing-across-sites):

| Field | Meaning |
| --- | --- |
| `geo_passes` | Repair passes run since the start |
| `geo_shards_repaired` | This site's shards (or full chunks) rebuilt from other sites |
| `geo_chunks_failed` | Failed repairs because too few sites answered, counted per pass |
| `geo_unrepairable` | Geo chunks the last pass couldn't rebuild |
| `geo_skipped` | Damaged geo chunks the last pass left alone because a residency rule keeps them off this site |
| `last_geo_pass_ms`, `last_geo_pass` | When the last pass ran, and its result (`null` before the first) |
`orphan_sweep` holds the [orphan sweep](/durability/healing#orphaned-chunks) totals since the node
started and the result of the last run (`null` before the first).

`POST /api/heal` verifies every chunk and repairs damaged shards now, and answers when it is done:

```json
{ "checked": 2203114, "damaged": 4, "repaired": 12, "lost": 0, "lost_chunks": [],
  "geo": { "checked": 81220, "damaged": 3, "repaired": 3, "failed": 0, "skipped": 0,
           "failed_chunks": [], "errors": [] } }
```

`lost_chunks` lists up to 100 hashes of chunks with too few good shards to rebuild. See
[Healing](/durability/healing).

On a site with [geo erasure coding](/replication/geo-erasure-coding#healing-across-sites), `geo` is
the repair from other sites that ends the pass (left out when there are no geo chunks to check).
Geo shards rebuilt that way don't count as lost.

| Field | Meaning |
| --- | --- |
| `checked` | Chunk references of geo versions checked |
| `damaged` | Chunks with this site's shards (or its full copy) missing or corrupt |
| `repaired` | Shards or full chunks rebuilt from other sites and written back |
| `failed` | Damaged chunks that couldn't be rebuilt because too few sites answered; tried again on the next pass |
| `skipped` | Damaged chunks of versions a residency rule keeps off this site, left alone |
| `failed_chunks` | Up to 100 hashes of chunks that couldn't be rebuilt |
| `errors` | Up to 10 distinct reasons |

`POST /api/heal/geo` runs only that repair, without verifying every chunk first, and answers the same
object as `geo`. It checks missing shards and the ones reads found bad. On a
[cluster](/deploy/cluster#geo-erasure-coding), call it on the leader: on a follower it checks
nothing (`checked: 0`).

`POST /api/gc` runs garbage collection now with the configured grace period. `?grace_secs=0` deletes
unreferenced chunks at once:

```json
{ "chunks_deleted": 120, "bytes_freed": 402331221, "uploads_aborted": 1 }
```

### Orphan sweep

`POST /api/gc/sweep` walks every chunk directory of this node and deletes chunk files no metadata
references, plus temp files of interrupted writes. It answers when it is done. See
[Orphaned chunks](/durability/healing#orphaned-chunks).

<ParamField query="dry_run" type="boolean" default="false">
  Only count what would be deleted.
</ParamField>

<ParamField query="min_age_secs" type="integer">
  Delete only files last modified longer ago than this. The default is `ZEE3_GC_GRACE`
  (`scanner.gc_grace_secs`); in cluster mode, the larger of `ZEE3_GC_GRACE` and `ZEE3_UPLOAD_TTL`.
  `0` is allowed, but then only the holds of writes in this process protect new chunks: don't use it
  on a node that serves traffic.
</ParamField>

```bash
curl -X POST "$ZEE3_ADMIN_URL/api/gc/sweep?dry_run=true" -H "Authorization: Bearer $TOKEN"
```

```json
{ "dry_run": true, "dirs": 4096, "chunks_checked": 2203128, "orphans": 14, "young": 2, "deleted": 12,
  "bytes_freed": 50331648, "tmp_files": 1, "tmp_bytes": 4194304, "duration_ms": 41200 }
```

| Field | Meaning |
| --- | --- |
| `dirs` | Chunk directories walked, over every disk and pool |
| `chunks_checked` | Chunk files looked at |
| `orphans` | Chunk files nothing references |
| `young` | Of those, too recent to delete; kept for now |
| `deleted`, `bytes_freed` | Orphaned chunk files deleted (in a dry run: that would be) and their bytes |
| `tmp_files`, `tmp_bytes` | Temp files of interrupted writes deleted (in a dry run: that would be) |
| `duration_ms` | How long the sweep took |

The sweep keeps to `ZEE3_HEAL_DUTY`, so on a large node it takes a while. One sweep runs at a time.

## Config export and import

`GET /api/config/export?secrets=false` answers the configuration document; `secrets=true` includes
every secret and needs `admin:UserAdmin` and `admin:ConfigUpdate`. The IAM part is included only for
callers with `admin:UserAdmin`.

`POST /api/config/import` takes that document and answers `{"applied": [...], "skipped": [...]}`. A
document whose `zee3_config` is not `1` answers `400`. See [Config export and import](/operations/config-export).

## Imports

An import copies buckets and objects from MinIO or another S3 store into this node. See
[Migrate from MinIO](/deploy/migrate-from-minio).

`POST /api/imports` answers `201` with the job:

<ParamField body="endpoint" type="string" required>
  The source's S3 API, like `http://minio.local:9000`.
</ParamField>

<ParamField body="access_key" type="string" required>
  An access key on the source.
</ParamField>

<ParamField body="secret_key" type="string" required>
  Its secret key. Shown as `***` afterwards.
</ParamField>

<ParamField body="region" type="string">
  The source's region.
</ParamField>

<ParamField body="buckets" type="string[]">
  Buckets to import; empty imports every bucket.
</ParamField>

<ParamField body="continuous" type="boolean" default="false">
  Keep importing what is new every `interval_secs` until stopped, for a cutover.
</ParamField>

<ParamField body="interval_secs" type="integer" default="300">
  The pause between passes in continuous mode.
</ParamField>

<ParamField body="concurrency" type="integer" default="8">
  Objects copied in parallel.
</ParamField>

<ParamField body="bucket_config" type="boolean" default="false">
  Also copy each bucket's Object Lock, default encryption, policy, lifecycle and tags.
</ParamField>

<ParamField body="mirror_deletes" type="boolean" default="false">
  Delete what the job imported and the source no longer lists.
</ParamField>

<ParamField body="mirror_dry_run" type="boolean" default="false">
  With `mirror_deletes`: only count and sample.
</ParamField>

`PATCH /api/imports/{id}` takes any of `mirror_deletes`, `mirror_dry_run`, `bucket_config`, `continuous`
and `interval_secs` and answers the job.

A job:

```json
{
  "id": "...", "request": { "endpoint": "http://minio.local:9000", "access_key": "minioadmin", "secret_key": "***",
    "region": "", "buckets": [], "continuous": true, "interval_secs": 300, "concurrency": 8 },
  "status": "waiting",
  "progress": { "passes": 1, "buckets": ["photos", "logs"], "bucket_index": 0, "marker": null,
    "objects_imported": 120443, "delete_markers_imported": 12, "bytes_imported": 912003344221,
    "skipped": 0, "failed": 0, "recent_errors": [], "pass_started_ms": 1794920000000, "last_pass_finished_ms": 1794920900000 },
  "created_ms": 1794919000000, "last_error": null
}
```

`progress` also has `deletions_mirrored` (every pass), `deletions_refused`, `deletions_planned` and
`deletion_samples` (this pass), and the job has `config.<bucket>.<object_lock|encryption|policy|lifecycle|tags>`
with `state`, `skipped`, `message` and `checked_ms`. See
[Migrate from MinIO](/deploy/migrate-from-minio#mirror-deletions).

`status` is `running`, `waiting` (continuous mode, between passes), `paused`, `done` or `failed`.
`pause` and `resume` answer the job. `DELETE` stops the job and forgets it; what was imported stays.
